# 2. Marco de elicitación holística y ética

## 2.1 Propósito

La ingeniería de requisitos de EcoLogística Huancayo busca identificar, analizar, validar y documentar las necesidades de los diferentes usuarios y actores relacionados con la planificación y ejecución de operaciones de distribución de última milla.

El proceso de elicitación considerará tanto las necesidades funcionales como las condiciones operativas, sociales, tecnológicas y ambientales que pueden influir en el uso del sistema.

---

## 2.2 Actores considerados

La identificación de requisitos considera los siguientes grupos:

- **Responsable de operaciones logísticas:** necesita planificar y supervisar las rutas de distribución.
- **Administrador del sistema:** necesita gestionar información operativa y controlar el acceso al sistema.
- **Conductor:** necesita consultar las rutas asignadas, entregas pendientes y alertas relevantes.
- **Cliente:** necesita proporcionar información relacionada con sus pedidos, horarios y condiciones de entrega.
- **Equipo de proyecto:** necesita validar requisitos, restricciones, calidad y comportamiento esperado del sistema.
- **Responsable académico:** verifica que la solución cumpla con los objetivos y entregables establecidos para el proyecto.

---

## 2.3 Técnicas de elicitación

Para identificar y validar las necesidades del sistema se consideran las siguientes técnicas:

| Técnica | Aplicación en EcoLogística Huancayo |
|---|---|
| **Entrevistas** | Recopilar necesidades y problemas de responsables logísticos y conductores. |
| **Observación** | Analizar las actividades relacionadas con planificación y entrega de pedidos. |
| **Cuestionarios** | Recopilar información de varios usuarios cuando las entrevistas individuales no sean suficientes. |
| **Análisis documental** | Revisar requisitos de la consigna, normativa aplicable y documentación relacionada con el contexto del proyecto. |
| **Prototipos** | Validar tempranamente la interfaz y flujo de las principales funcionalidades. |
| **Revisión iterativa** | Confirmar los requisitos durante las iteraciones del proyecto. |

---

## 2.4 Consideraciones del contexto local

Los requisitos deberán adaptarse al ámbito geográfico y operativo definido para Huancayo.

El sistema deberá considerar que las condiciones reales de las operaciones de distribución pueden variar según:

- ubicación de los clientes;
- condiciones de las vías;
- disponibilidad de vehículos;
- horarios de atención;
- condiciones de entrega;
- cambios operativos durante la jornada.

La información geográfica utilizada por el sistema deberá ser validada antes de emplearse como base para decisiones de planificación.

---

## 2.5 Perspectiva ética

La obtención y utilización de información deberá respetar los principios de:

- minimización de datos;
- confidencialidad;
- uso legítimo de la información;
- transparencia;
- control de acceso;
- protección de datos personales.

El sistema no deberá utilizar información personal innecesaria para cumplir las funciones definidas.

Los resultados generados por el sistema deberán poder ser revisados por los responsables correspondientes, especialmente cuando una decisión de asignación o ruta afecte la operación.

# 3. Especificación de requisitos funcionales

Los requisitos funcionales se expresan de manera atómica y describen exclusivamente qué debe realizar el sistema, evitando términos ambiguos y especificaciones tecnológicas prematuras.

---

## RF-001: Registrar vehículo

**Descripción Atómica:** El sistema debe registrar un vehículo cuando un usuario autorizado proporcione la placa, tipo de vehículo, capacidad de carga, consumo de combustible, factor de emisión de CO₂ y año de fabricación válidos.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** un usuario autenticado con permisos de gestión de flota y un vehículo no registrado.  
> **CUANDO** proporcione todos los datos obligatorios con valores válidos.  
> **ENTONCES** el sistema debe registrar el vehículo y confirmar la operación.

#### Ruta Feliz
> **DADO** un usuario autorizado y un vehículo con datos válidos.  
> **CUANDO** proporcione información adicional permitida.  
> **ENTONCES** el sistema debe registrar el vehículo conservando la información proporcionada.

#### Ruta Infeliz
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione una placa ya registrada o un dato obligatorio inválido.  
> **ENTONCES** el sistema debe rechazar el registro y mostrar el motivo.

---

## RF-002: Consultar vehículos

**Descripción Atómica:** El sistema debe mostrar la información registrada de los vehículos cuando un usuario autorizado solicite consultar la flota.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** un usuario autorizado.  
> **CUANDO** solicite consultar la flota.  
> **ENTONCES** el sistema debe mostrar los vehículos registrados y sus principales características.

#### Ruta Feliz
> **DADO** un usuario autorizado.  
> **CUANDO** aplique un criterio de búsqueda válido.  
> **ENTONCES** el sistema debe mostrar los vehículos que coincidan con el criterio.

#### Ruta Infeliz
> **DADO** un usuario autorizado.  
> **CUANDO** utilice un criterio de búsqueda inválido.  
> **ENTONCES** el sistema debe rechazar el criterio y mostrar un mensaje explicativo.

---

## RF-003: Registrar pedido

**Descripción Atómica:** El sistema debe registrar un pedido cuando un usuario autorizado proporcione cliente, dirección, coordenadas, peso, volumen, ventana de tiempo, prioridad y tipo de producto válidos.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** un usuario autorizado y un cliente registrado.  
> **CUANDO** proporcione todos los datos obligatorios válidos.  
> **ENTONCES** el sistema debe registrar el pedido y asignarle un identificador único.

#### Ruta Feliz
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione una referencia adicional válida para la ubicación.  
> **ENTONCES** el sistema debe conservar la referencia asociada al pedido.

#### Ruta Infeliz
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione una coordenada inválida, una ventana horaria inconsistente o un peso no válido.  
> **ENTONCES** el sistema debe rechazar el registro e informar los errores detectados.

---

## RF-004: Consultar pedidos

**Descripción Atómica:** El sistema debe mostrar la información de los pedidos registrados cuando un usuario autorizado solicite su consulta.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** un usuario autorizado.  
> **CUANDO** solicite consultar los pedidos.  
> **ENTONCES** el sistema debe mostrar los pedidos disponibles con su información principal.

#### Ruta Feliz
> **DADO** un usuario autorizado.  
> **CUANDO** filtre los pedidos por estado, prioridad o fecha válida.  
> **ENTONCES** el sistema debe mostrar los pedidos que coincidan con el filtro.

#### Ruta Infeliz
> **DADO** un usuario autorizado.  
> **CUANDO** utilice un filtro no válido.  
> **ENTONCES** el sistema debe mostrar un mensaje de validación y mantener la consulta consistente.

---

### Criterios de Aceptación

#### Ruta Gold

> **CUANDO** proporcione los datos obligatorios válidos.  
> **ENTONCES** el sistema debe registrar al conductor y confirmar la operación.

#### Ruta Feliz
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione información complementaria válida del conductor.  
> **ENTONCES** el sistema debe conservar dicha información asociada al registro.

#### Ruta Infeliz
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione un documento de identidad o licencia ya registrados.  
> **ENTONCES** el sistema debe rechazar el registro y mostrar el motivo.

---

## RF-006: Registrar cliente

**Descripción Atómica:** El sistema debe registrar un cliente cuando un usuario autorizado proporcione la información requerida para identificarlo y gestionar sus entregas.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione información válida del cliente.  
> **ENTONCES** el sistema debe registrar al cliente.

#### Ruta Feliz
> **DADO** un usuario autorizado.  
> **CUANDO** proporcione preferencias de horario y referencias de entrega válidas.  
> **ENTONCES** el sistema debe asociarlas al cliente.

#### Ruta Infeliz
> **DADO** un usuario autorizado.  
> **CUANDO** falte información obligatoria o existan datos duplicados.  
> **ENTONCES** el sistema debe rechazar el registro e informar la causa.

---

## RF-007: Generar ruta optimizada

**Descripción Atómica:** El sistema debe generar una propuesta de ruta para un conjunto de pedidos seleccionados cuando existan vehículos disponibles y condiciones operativas válidas.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** un conjunto de pedidos válidos, vehículos disponibles y condiciones de planificación válidas.  
> **CUANDO** el usuario autorizado solicite la generación de rutas.  
> **ENTONCES** el sistema debe generar una propuesta de asignación y recorrido.

#### Ruta Feliz
> **DADO** un conjunto de pedidos y vehículos disponibles.  
> **CUANDO** una alternativa de recorrido no pueda utilizarse debido a una restricción válida.  
> **ENTONCES** el sistema debe evaluar y proponer una alternativa compatible con las condiciones disponibles.

#### Ruta Infeliz
> **DADO** un conjunto de pedidos.  
> **CUANDO** no exista una combinación válida de recursos para atenderlos.  
> **ENTONCES** el sistema debe informar que no existe una solución válida y evitar asignaciones incorrectas.

---

## RF-008: Visualizar ruta en mapa

**Descripción Atómica:** El sistema debe mostrar el recorrido generado y sus puntos de entrega cuando exista una ruta válida.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** una ruta válida generada por el sistema.  
> **CUANDO** el usuario solicite visualizarla.  
> **ENTONCES** el sistema debe mostrar el recorrido y los puntos de entrega correspondientes.

#### Ruta Feliz
> **DADO** una ruta válida.  
> **CUANDO** el usuario seleccione una entrega específica.  
> **ENTONCES** el sistema debe mostrar la información asociada a ese punto.

#### Ruta Infeliz
> **DADO** una ruta previamente generada.  
> **CUANDO** no exista información cartográfica disponible para representarla.  
> **ENTONCES** el sistema debe informar la imposibilidad de visualización y conservar la ruta registrada.

---

## RF-009: Mostrar indicadores logísticos y ambientales

**Descripción Atómica:** El sistema debe calcular y mostrar indicadores de operación cuando existan rutas con datos suficientes para realizar la evaluación.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** una o más rutas procesadas.  
> **CUANDO** el usuario autorizado consulte los indicadores.  
> **ENTONCES** el sistema debe mostrar los valores calculados de distancia, combustible, emisiones y cumplimiento de entregas.

#### Ruta Feliz
> **DADO** rutas procesadas.  
> **CUANDO** el usuario seleccione un periodo o conjunto de rutas válido.  
> **ENTONCES** el sistema debe actualizar los indicadores para el subconjunto seleccionado.

#### Ruta Infeliz
> **DADO** una operación sin datos suficientes para calcular un indicador.  
> **CUANDO** el usuario consulte dicho indicador.  
> **ENTONCES** el sistema debe indicar que el valor no está disponible y evitar mostrar un resultado incorrecto.

---

## RF-010: Reoptimizar rutas ante cambios operativos

**Descripción Atómica:** El sistema debe generar una nueva propuesta de ruta cuando un usuario autorizado registre un cambio que afecte una planificación existente.

**Prioridad:** Alta

### Criterios de Aceptación

#### Ruta Gold
> **DADO** una planificación existente y un cambio operativo válido.  
> **CUANDO** el usuario solicite la reoptimización.  
> **ENTONCES** el sistema debe generar una nueva propuesta considerando el cambio registrado.

#### Ruta Feliz
> **DADO** una planificación existente.  
> **CUANDO** se registre una modificación que no invalide todas las asignaciones actuales.  
> **ENTONCES** el sistema debe conservar las asignaciones válidas y recalcular las afectadas.

#### Ruta Infeliz
> **DADO** una planificación existente.  
> **CUANDO** ocurra un cambio que impida generar una solución válida.  
> **ENTONCES** el sistema debe informar el problema y conservar la última planificación válida.

# 4. Criterios generales de validación

Los requisitos funcionales deberán verificarse mediante pruebas funcionales y de aceptación.

Cada requisito deberá poder relacionarse posteriormente con:

- uno o más usuarios;
- una o más reglas de negocio;
- requisitos no funcionales aplicables;
- casos de prueba;
- componentes de la solución.

La trazabilidad será mantenida durante las siguientes etapas del proyecto.

---

# 5. Control de cambios

Los requisitos funcionales podrán evolucionar durante las iteraciones del proyecto.

Cualquier cambio significativo deberá:

1. Identificar el requisito afectado.
2. Registrar la modificación.
3. Analizar su impacto sobre otros artefactos.
4. Validar el cambio con los interesados correspondientes.
5. Actualizar la versión del documento cuando corresponda.

La versión inicial del presente documento corresponde a **V_1_0_0**.
