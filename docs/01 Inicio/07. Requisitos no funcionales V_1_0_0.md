# 2. Propósito

Los requisitos no funcionales de EcoLogística Huancayo establecen los atributos de calidad, restricciones de comportamiento y niveles medibles que deberá cumplir el sistema.

Estos requisitos se expresan mediante escenarios de calidad y métricas cuantitativas, siguiendo el enfoque indicado por la consigna y tomando como referencia las características de calidad de ISO/IEC 25010.

No se utilizarán términos ambiguos como "rápido", "fácil", "eficiente" o "seguro" sin una medida verificable asociada.

# 4. Escenarios de calidad detallados

## RNF-001: Rendimiento de generación de rutas

### Categoría
Rendimiento.

### Escenario de calidad

**Fuente:** Usuario autorizado.

**Estímulo:** Solicitud de generación de rutas para un escenario de prueba de hasta 150 pedidos y 15 vehículos.

**Entorno:** Operación normal con los servicios necesarios disponibles.

**Artefacto:** Motor de generación y optimización de rutas.

**Respuesta:** El sistema procesa la solicitud, ejecuta la estrategia de optimización y devuelve una solución válida o informa que no existe una solución válida.

**Medida / SLA:** El tiempo transcurrido desde el inicio del procesamiento hasta la disponibilidad de la solución no deberá superar los **45 segundos**.

---

## RNF-002: Rendimiento de reoptimización

### Categoría
Rendimiento.

### Escenario de calidad

**Fuente:** Usuario autorizado.

**Estímulo:** Registro de un cambio que afecta una planificación existente.

**Entorno:** Operación normal.

**Artefacto:** Módulo de reoptimización.

**Respuesta:** El sistema recalcula las asignaciones afectadas y presenta una nueva propuesta válida.

**Medida / SLA:** El proceso de reoptimización deberá completarse en un tiempo máximo de **30 segundos**.

---

## RNF-003: Control de acceso

### Categoría
Seguridad.

### Escenario de calidad

**Fuente:** Usuario autenticado o no autenticado.

**Estímulo:** Solicitud de acceso a una funcionalidad protegida.

**Entorno:** Operación normal.

**Artefacto:** Mecanismo de autenticación y autorización.

**Respuesta:** El sistema permite el acceso únicamente cuando el usuario presenta credenciales válidas y posee los permisos correspondientes.

**Medida / SLA:** El 100 % de los endpoints clasificados como protegidos deberá requerir autenticación y autorización verificable durante las pruebas de seguridad.

---

## RNF-004: Protección frente a vulnerabilidades web

### Categoría
Seguridad.

### Escenario de calidad

**Fuente:** Evaluador de seguridad.

**Estímulo:** Intento de explotación de vulnerabilidades incluidas en OWASP Top 10.

**Entorno:** Entorno de pruebas previo a la liberación del MVP.

**Artefacto:** Aplicación web y API.

**Respuesta:** La aplicación deberá rechazar o neutralizar solicitudes maliciosas y registrar los eventos relevantes.

**Medida / SLA:** La versión candidata a entrega deberá presentar **0 vulnerabilidades críticas OWASP Top 10 sin mitigar**.

---

## RNF-005: Disponibilidad

### Categoría
Disponibilidad.

### Escenario de calidad

**Fuente:** Usuario operativo.

**Estímulo:** Solicitud de una operación durante el horario operativo.

**Entorno:** Horario comprendido entre 05:00 y 22:00.

**Artefacto:** Plataforma web y servicios de soporte.

**Respuesta:** El sistema debe permanecer disponible para ejecutar las funcionalidades habilitadas.

**Medida / SLA:** La disponibilidad objetivo será de al menos **99.5 % durante el horario operativo**.

---

## RNF-006: Usabilidad para conductores

### Categoría
Usabilidad.

### Escenario de calidad

**Fuente:** Conductor participante de la prueba.

**Estímulo:** Consulta de la ruta asignada y las entregas pendientes.

**Entorno:** Sesión de prueba con datos representativos.

**Artefacto:** Interfaz correspondiente al modo conductor.

**Respuesta:** El usuario debe localizar la ruta y las entregas necesarias para iniciar su recorrido.

**Medida / SLA:** Al menos **90 % de los usuarios de prueba** deberá completar la tarea sin asistencia directa.

---

## RNF-007: Accesibilidad

### Categoría
Accesibilidad.

### Escenario de calidad

**Fuente:** Usuario con diferentes capacidades de interacción.

**Estímulo:** Navegación y utilización de las funcionalidades principales.

**Entorno:** Interfaz web del MVP.

**Artefacto:** Componentes de interfaz, formularios, navegación y visualización de información.

**Respuesta:** El usuario deberá poder acceder e interactuar con las funcionalidades definidas bajo los criterios de accesibilidad establecidos.

**Medida / SLA:** Las funcionalidades prioritarias del MVP deberán cumplir los criterios aplicables de **WCAG 2.1 nivel AA** establecidos para las pruebas de accesibilidad.

---

## RNF-008: Escalabilidad

### Categoría
Escalabilidad.

### Escenario de calidad

**Fuente:** Responsable de operaciones.

**Estímulo:** Incremento de la cantidad diaria de pedidos y vehículos.

**Entorno:** Prueba de carga planificada.

**Artefacto:** Plataforma completa y motor de procesamiento.

**Respuesta:** El sistema deberá continuar ejecutando las funcionalidades principales sin errores funcionales críticos.

**Medida / SLA:** El sistema deberá soportar un escenario de hasta **1,000 pedidos diarios y 50 vehículos** durante las pruebas definidas.

---

## RNF-009: Compatibilidad

### Categoría
Compatibilidad.

### Escenario de calidad

**Fuente:** Usuario final.

**Estímulo:** Acceso al sistema desde navegadores y dispositivos incluidos en la matriz de compatibilidad.

**Entorno:** Entornos de prueba definidos por el proyecto.

**Artefacto:** Interfaz web.

**Respuesta:** Las funcionalidades principales deberán mantener el comportamiento esperado en los entornos soportados.

**Medida / SLA:** El 100 % de las funcionalidades prioritarias deberá superar las pruebas de compatibilidad en los entornos definidos como soportados.

---

## RNF-010: Mantenibilidad

### Categoría
Mantenibilidad.

### Escenario de calidad

**Fuente:** Integrante del equipo de desarrollo.

**Estímulo:** Modificación de un módulo del sistema.

**Entorno:** Entorno de desarrollo y pruebas.

**Artefacto:** Código fuente y pruebas asociadas.

**Respuesta:** El cambio deberá poder implementarse sin afectar las funcionalidades que no formen parte de la modificación.

**Medida / SLA:** Las pruebas automatizadas existentes relacionadas con el cambio deberán permanecer satisfactorias y no deberán introducirse defectos críticos conocidos antes de integrar la modificación.

---

## RNF-011: Eficiencia energética

### Categoría
Eficiencia energética / Green Software.

### Escenario de calidad

**Fuente:** Usuario o proceso del sistema.

**Estímulo:** Ejecución de consultas y procesamiento de información.

**Entorno:** Operación normal.

**Artefacto:** Backend, consultas de base de datos y transferencia de datos.

**Respuesta:** El sistema deberá procesar únicamente la información necesaria para atender la solicitud y evitar operaciones redundantes.

**Medida / SLA:** Las consultas críticas deberán recuperar únicamente los campos necesarios para la operación y deberán ser evaluadas mediante revisión técnica y pruebas de rendimiento.

---

## RNF-012: Fiabilidad y consistencia

### Categoría
Fiabilidad.

### Escenario de calidad

**Fuente:** Sistema o servicio externo.

**Estímulo:** Interrupción inesperada durante una operación de escritura o generación de asignaciones.

**Entorno:** Operación normal o escenario de prueba controlado.

**Artefacto:** Módulos transaccionales y persistencia de datos.

**Respuesta:** El sistema deberá evitar estados parcialmente confirmados y deberá informar el error al usuario.

**Medida / SLA:** El 100 % de los casos de prueba de transacciones interrumpidas deberá finalizar con datos consistentes y sin registros parcialmente confirmados.

# 6. Criterios generales de medición

Los requisitos no funcionales deberán verificarse mediante pruebas y evidencias documentadas.

Las métricas deberán:

- poseer un valor o condición verificable;
- poder medirse mediante una prueba;
- estar asociadas a un escenario concreto;
- evitar términos subjetivos;
- conservar trazabilidad con los requisitos funcionales y reglas de negocio correspondientes.

Los valores definidos en este documento podrán ser revisados cuando se disponga de resultados de pruebas y datos reales del proyecto.

---

# 7. Control de cambios

Cualquier modificación de un requisito no funcional deberá analizar su impacto sobre:

- requisitos funcionales;
- arquitectura;
- diseño de base de datos;
- pruebas;
- seguridad;
- rendimiento;
- documentación relacionada.

Las modificaciones sustanciales deberán reflejarse en la versión correspondiente del documento.
