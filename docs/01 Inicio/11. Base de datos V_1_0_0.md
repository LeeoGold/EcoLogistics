## 2. Propósito

Definir el modelo conceptual, lógico y físico de la base de datos de EcoLogística Huancayo, manteniendo trazabilidad con los requisitos funcionales, requisitos no funcionales, usuarios y reglas de negocio previamente establecidos.

La base de datos deberá permitir gestionar la información necesaria para vehículos, conductores, clientes, pedidos, rutas, asignaciones, entregas y usuarios del sistema.

La solución seleccionada en el documento 10 utiliza PostgreSQL como sistema gestor de base de datos.

---

# 3. Criterios de diseño

El diseño seguirá los siguientes criterios:

- Integridad referencial mediante claves primarias y foráneas.
- Evitar duplicidad innecesaria de información.
- Separar entidades con responsabilidades diferentes.
- Mantener trazabilidad de las operaciones relevantes.
- Permitir consultas eficientes para planificación y seguimiento.
- Mantener una estructura normalizada hasta tercera forma normal (3FN).
- Utilizar identificadores estables para las entidades principales.

# 6. Normalización hasta 3FN

## Primera Forma Normal (1FN)

Se garantiza que:

- Cada atributo contiene un solo valor.
- No existen grupos repetitivos.
- Cada registro puede identificarse mediante una clave primaria.

Por ejemplo, las preferencias del cliente se mantienen como atributos separados y no como una lista dentro de un único campo.

## Segunda Forma Normal (2FN)

Las entidades poseen claves primarias identificables y los atributos dependen de la totalidad de su clave.

El modelo evita almacenar atributos de una entidad distinta dentro de otra cuando existe una relación independiente.

## Tercera Forma Normal (3FN)

Los atributos no clave dependen únicamente de la clave primaria de su propia entidad y no de otros atributos no clave.

Por ejemplo:

- Los datos del cliente se almacenan en `clientes`.
- Los datos del pedido se almacenan en `pedidos`.
- Los datos del vehículo se almacenan en `vehiculos`.
- La relación entre ruta y pedido se almacena en `detalle_ruta`.

Esto reduce redundancia y facilita el mantenimiento de la información.

# 7. Reglas de integridad de datos

La base de datos aplicará, como mínimo:

- Claves primarias para identificar entidades.
- Claves foráneas para mantener relaciones.
- Restricciones `NOT NULL` para datos obligatorios.
- Restricciones `UNIQUE` para datos que no deben duplicarse.
- Restricciones `CHECK` para validar rangos.
- Índices sobre campos de búsqueda frecuente.
- Integridad referencial entre entidades relacionadas.

# 8. Modelo físico — DDL SQL

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE roles (
    rol_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    nombre VARCHAR(50) NOT NULL UNIQUE,
    descripcion VARCHAR(255)
);

CREATE TABLE usuarios (
    usuario_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rol_id UUID NOT NULL REFERENCES roles(rol_id),
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'ACTIVO',
    creado_en TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE conductores (
    conductor_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    usuario_id UUID UNIQUE REFERENCES usuarios(usuario_id),
    nombre_completo VARCHAR(150) NOT NULL,
    documento_identidad VARCHAR(20) NOT NULL UNIQUE,
    licencia VARCHAR(30) NOT NULL UNIQUE,
    categoria_licencia VARCHAR(20) NOT NULL,
    anios_experiencia INTEGER NOT NULL CHECK (anios_experiencia >= 0),
    disponibilidad_inicio TIME NOT NULL,
    disponibilidad_fin TIME NOT NULL,
    contacto VARCHAR(30) NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'ACTIVO',
    CHECK (disponibilidad_inicio < disponibilidad_fin)
);

CREATE TABLE vehiculos (
    vehiculo_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    placa VARCHAR(15) NOT NULL UNIQUE,
    tipo VARCHAR(30) NOT NULL,
    capacidad_kg NUMERIC(10,2) NOT NULL CHECK (capacidad_kg > 0),
    consumo_km_l NUMERIC(10,3) NOT NULL CHECK (consumo_km_l > 0),
    factor_co2_kg_km NUMERIC(10,4) NOT NULL CHECK (factor_co2_kg_km >= 0),
    anio_fabricacion INTEGER NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'DISPONIBLE'
);

CREATE TABLE clientes (
    cliente_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    nombre VARCHAR(150) NOT NULL,
    contacto VARCHAR(30),
    direccion_referencia VARCHAR(255) NOT NULL,
    latitud NUMERIC(10,7) NOT NULL,
    longitud NUMERIC(10,7) NOT NULL,
    horario_preferido_inicio TIME,
    horario_preferido_fin TIME,
    restricciones_acceso VARCHAR(255),
    creado_en TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (
        (horario_preferido_inicio IS NULL AND horario_preferido_fin IS NULL)
        OR
        (horario_preferido_inicio < horario_preferido_fin)
    )
);

CREATE TABLE pedidos (
    pedido_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cliente_id UUID NOT NULL REFERENCES clientes(cliente_id),
    peso_kg NUMERIC(10,2) NOT NULL CHECK (peso_kg > 0),
    volumen_m3 NUMERIC(10,4) NOT NULL CHECK (volumen_m3 > 0),
    ventana_inicio TIMESTAMPTZ NOT NULL,
    ventana_fin TIMESTAMPTZ NOT NULL,
    prioridad VARCHAR(20) NOT NULL,
    tipo_producto VARCHAR(30) NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'PENDIENTE',
    referencia_entrega VARCHAR(255),
    creado_en TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (ventana_inicio < ventana_fin),
    CHECK (prioridad IN ('EXPRESS', 'ESTANDAR', 'ECONOMICO')),
    CHECK (tipo_producto IN ('PERECEDERO', 'NO_PERECEDERO'))
);

CREATE TABLE rutas (
    ruta_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    fecha_planificada DATE NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'PLANIFICADA',
    distancia_km NUMERIC(12,3),
    tiempo_total_min NUMERIC(12,2),
    combustible_l NUMERIC(12,3),
    emisiones_co2_kg NUMERIC(12,3),
    penalizacion_total NUMERIC(12,3),
    creada_en TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE asignaciones_conductor (
    asignacion_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ruta_id UUID NOT NULL REFERENCES rutas(ruta_id),
    conductor_id UUID NOT NULL REFERENCES conductores(conductor_id),
    vehiculo_id UUID NOT NULL REFERENCES vehiculos(vehiculo_id),
    hora_inicio TIMESTAMPTZ NOT NULL,
    hora_fin TIMESTAMPTZ,
    CHECK (hora_fin IS NULL OR hora_inicio < hora_fin)
);

CREATE TABLE detalle_ruta (
    detalle_ruta_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ruta_id UUID NOT NULL REFERENCES rutas(ruta_id),
    pedido_id UUID NOT NULL REFERENCES pedidos(pedido_id),
    secuencia INTEGER NOT NULL CHECK (secuencia > 0),
    llegada_estimada TIMESTAMPTZ,
    salida_estimada TIMESTAMPTZ,
    distancia_tramo_km NUMERIC(12,3),
    UNIQUE (ruta_id, secuencia),
    UNIQUE (ruta_id, pedido_id)
);

CREATE TABLE entregas (
    entrega_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    pedido_id UUID NOT NULL REFERENCES pedidos(pedido_id),
    ruta_id UUID NOT NULL REFERENCES rutas(ruta_id),
    estado VARCHAR(20) NOT NULL DEFAULT 'PENDIENTE',
    hora_entrega TIMESTAMPTZ,
    observacion VARCHAR(255)
);

CREATE TABLE incidencias (
    incidencia_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    pedido_id UUID REFERENCES pedidos(pedido_id),
    ruta_id UUID REFERENCES rutas(ruta_id),
    usuario_id UUID REFERENCES usuarios(usuario_id),
    tipo VARCHAR(50) NOT NULL,
    descripcion VARCHAR(500) NOT NULL,
    registrada_en TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    estado VARCHAR(20) NOT NULL DEFAULT 'ABIERTA'
);
```


# 10. Reglas de integridad relacionadas

La implementación de la base de datos deberá permitir soportar, entre otras, las siguientes reglas:

| Regla | Soporte en BD |
|---|---|
| RN-001 Unicidad de vehículos | `UNIQUE(placa)` |

| RN-005 Vehículos disponibles | Campo `estado` en vehículos |
| RN-006 Conductores disponibles | Campo `estado` y disponibilidad horaria |

Las reglas de negocio que requieren cálculos o validaciones dinámicas deberán aplicarse en la capa de negocio y posteriormente verificarse mediante pruebas.

# 14. Conclusión

El modelo propuesto proporciona una estructura relacional para administrar los principales datos de EcoLogística Huancayo.

El diseño separa usuarios, roles, conductores, vehículos, clientes, pedidos, rutas, asignaciones, entregas e incidencias, permitiendo mantener integridad referencial y una estructura normalizada hasta 3FN.

El modelo físico utiliza PostgreSQL y define claves primarias, claves foráneas, restricciones, índices y estructuras DDL que podrán utilizarse posteriormente como base para la implementación del sistema.

La versión inicial del presente documento corresponde a **V_1_0_0**.
