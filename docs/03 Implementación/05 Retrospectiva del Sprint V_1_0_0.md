# 05 Retrospectiva del Sprint V_1_0_0

[← Volver al README](../../README.md)

## 1. Método utilizado

Se utiliza el formato **Keep / Start / Stop**, orientado a identificar acciones concretas para Sprint 2.

## 2. Keep — Mantener

- Mantener el uso de Jira para relacionar HUs y subtareas.
- Mantener los checkpoints frecuentes del trabajo para disminuir el riesgo de pérdida de progreso.
- Mantener el desarrollo incremental sobre un módulo funcional antes de ampliar el alcance.

## 3. Start — Empezar

- Empezar a registrar evidencia de pruebas junto con cada HU implementada.
- Empezar a reflejar en Jira el estado real de cada subtarea el mismo día en que se realiza el trabajo.
- Empezar la implementación utilizando desde el inicio la separación modular solicitada para frontend y backend.

## 4. Stop — Dejar de hacer

- Dejar de considerar una HU como cerrada únicamente porque su implementación existe; primero debe existir evidencia de pruebas y DoD.
- Dejar de acumular cambios sin un checkpoint remoto cuando la conectividad lo permita.
- Dejar de concentrar responsabilidades de frontend o backend en pocos archivos si la consigna exige separación clara.

## 5. Compromisos medibles para Sprint 2

| Compromiso | Indicador | Meta | Responsable |
|---|---|---|---|
| Registrar estados de subtareas en Jira de forma sincronizada con el trabajo | Subtareas actualizadas | 100 % de subtareas trabajadas actualizadas en la misma sesión | Equipo de desarrollo |
| Aportar evidencia de pruebas | HUs con evidencia de prueba | 100 % de HUs implementadas antes de pasar a Listo | Equipo de desarrollo |
| Crear checkpoints remotos | Push de control | Al menos 1 push por sesión de desarrollo cuando exista conectividad | Equipo de desarrollo |
| Mantener arquitectura modular | Módulos con responsabilidades separadas | Cada funcionalidad nueva debe respetar la estructura definida antes de integrarse | Equipo de desarrollo |

## 6. Aprendizajes

El Sprint 1 muestra que disponer de una implementación funcional no es suficiente para cerrar una historia. También son necesarios el registro correcto en Jira, las pruebas, la evidencia y la coincidencia entre documentación, tablero y código.
